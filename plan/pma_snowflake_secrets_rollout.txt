================================================================================
PMA SPARK STAT SNOWFLAKE SECRET CONTAINERS — ROLLOUT RUNBOOK
Date: 2026-09-15 to 2026-09-17
Ticket: MIST-206719
================================================================================

GOAL: Create per-environment Secret Manager containers (AWS Secrets Manager /
      GCP Secret Manager) for the PMA Spark stat Snowflake credentials + key,
      populated from a single global source-of-truth secret, so EMR/Dataproc
      workloads in each environment can read them locally instead of reaching
      into the shared global AWS account at runtime.

REPOS TOUCHED:
  - mistsys/iac                (secret container terragrunt configs)
  - mistsys/spark_jobs          (secret ID lookup dicts consumed at runtime)
  - mistsys/terraform-aws-coreinfra (EMR IAM access — follow-up, not yet merged)

PREREQUISITES: aws-okta / gcloud CLI + relevant AWS profiles and GCP service
account impersonation permissions (see per-env tables in Phase 2). No VPN
connection/change is required for any command in this runbook (Secrets
Manager, Secret Manager, and Terragrunt/Terraform API calls all go over
public endpoints via aws-okta/gcloud auth).

================================================================================
PHASE 0 — BACKGROUND / NAMING HISTORY
================================================================================

Original secret names (first PR pass):
  pma_spark_stat_snowflake_credentials_production
  pma_spark_stat_snowflake_key_production

Iteration 1: AWS regional envs (use1prod2-aws, apse2prod5-aws, eu-aws) were
using a literal "production" path segment even though they are not the
production tier. Fixed to use each env's own Airflow ENV shortname, e.g.:
  mist/eu/airflow2/pma_spark_stat_snowflake_credentials_production
  mist/use1prod2/airflow2/pma_spark_stat_snowflake_key_production
(Confirmed via mist-airflow-operators/operators/config.py: ENV env var is the
per-region shortname, not a tier literal, except for the two actual
"production" clusters aws-production / gcp-production.)

Iteration 2 (final): dropped the redundant "spark_" segment entirely so the
per-env secret names match the global source-of-truth secrets exactly:
  pma_spark_stat_snowflake_credentials_production -> pma_stat_snowflake_credentials_production
  pma_spark_stat_snowflake_key_production          -> pma_snowflake_key_production

NOTE (GCP quirk): In gcp-terraform-modules//modules/secret, secret_id is
derived as `basename(get_terragrunt_dir())` — the directory name IS the
secret name. So GCP env renames required `git mv` on the terragrunt
directories, not just editing a `name` string (unlike AWS).

PHASE 2 — PER-ENVIRONMENT DESTROY -> APPLY -> POPULATE CYCLE
================================================================================

Because the secret name/path changed mid-flight, any already-applied
old-named secrets had to be deleted before applying the new-named
containers. Generic template used per environment:

GENERIC TEMPLATE (kept for future secrets that follow this same pattern):

--- AWS template ---
aws-okta exec <env-admin-profile> -- \
  aws secretsmanager delete-secret \
    --secret-id "mist/<env-path>/airflow2/<old_secret_name>" \
    --force-delete-without-recovery --region <region>

cd <env>-aws/auto/secrets/<new_secret_dir> && terragrunt apply

./scripts/copy_global_pma_secret.sh --target=aws \
  --secret=mist/<env-path>/airflow2/<new_secret_name> \
  --global-secret=mist/global/airflow2/<new_secret_name> \
  --region=<region>

--- GCP template ---
git checkout rvyom/mist-206719-<env>-gcp-pma-spark-stat-snowflake
REPO_ROOT=$(git rev-parse --show-toplevel)
export GOOGLE_OAUTH_ACCESS_TOKEN=$(gcloud auth print-access-token \
  --impersonate-service-account <env-sa>@mist-infrastructure-iam.iam.gserviceaccount.com)
PROJECT=$(cd "${REPO_ROOT}/<env>-gcp/boot/projects" && terragrunt output -json service_projects | jq -r '.dataproc')

gcloud secrets delete <old_secret_name> --project="${PROJECT}" --quiet \
  --impersonate-service-account=<env-sa>@mist-infrastructure-iam.iam.gserviceaccount.com || true

cd "${REPO_ROOT}/<env>-gcp/auto/secrets/<new_secret_name>" && terragrunt apply

"${REPO_ROOT}/scripts/copy_global_pma_secret.sh" --target=gcp \
  --secret=<new_secret_name> \
  --global-secret=mist/global/airflow2/<new_secret_name> \
  --project="${PROJECT}" \
  --impersonate-service-account=<env-sa>@mist-infrastructure-iam.iam.gserviceaccount.com

PHASE 4 — SPARK_JOBS RUNTIME LOOKUP FIX
================================================================================

Repo: mistsys/spark_jobs, file: report/__init__.py, PR #3770,
branch: rvyom-fix-snowflake-key-placeholder-injection

Bug found: _SNOWFLAKE_CREDENTIALS_AWS_SECRET_IDS / _SNOWFLAKE_KEY_AWS_SECRET_IDS
(and GCP equivalents) only had "staging"/"production" dict keys. Airflow's
ENV var for regional envs is the region shortname (e.g. "eu", "use1prod2",
"apse2prod5", "asne1prod7", "aso1prod5", "euwe1prod3", "mec1prod6",
"mec2prod6", "usc1prod4", "nane1prod1") — so lookups for all 10 regional
envs would silently resolve to None.

Fix applied:
  - Added missing per-env keys for the 3 AWS regional envs (eu, use1prod2,
    apse2prod5).
  - Added missing per-env keys for the 7 GCP regional envs (asne1prod7,
    aso1prod5, euwe1prod3, mec1prod6, mec2prod6, usc1prod4, nane1prod1).
  - Renamed all dict values to the final naming (dropped "spark"/"stat"
    segment as applicable) to match the renamed iac secrets.

PHASE 8 — VERIFICATION: CONFIRM ALL SECRETS MATCH GLOBAL SOURCE
================================================================================

Verifies not just that each secret exists/non-empty, but that its VALUE
exactly matches the global source-of-truth secret it was copied from. Uses
byte-exact comparison via temp files + `cmp` (same method
copy_global_pma_secret.sh itself uses to verify at copy time) rather than
`aws ... --output text`, which can subtly reformat strings and produce false
MISMATCH results. Run from the iac repo root (any branch). Requires the
"secrets-writer" AWS profile (global account) in addition to each env's
admin profile/SA.

Also saved as a standalone, re-runnable script in this same repo:
  plan/pma_snowflake_secrets_verify.sh
Run it with: bash plan/pma_snowflake_secrets_verify.sh (from anywhere --
it cd's into the iac repo root itself via `git rev-parse --show-toplevel`,
so it must be invoked while your shell is inside a clone of mistsys/iac).

Inline copy of the same script (kept here for reference in case the repo

compare_files() {
  local env="$1" secret="$2" got="$3" expected="$4"
  if [ ! -s "$got" ]; then
    echo "FAIL      $env  $secret  -> not found / empty"
  elif cmp -s "$got" "$expected"; then
    echo "OK        $env  $secret  -> matches global"
  else
    echo "MISMATCH  $env  $secret  -> does NOT match global"

Output prints "OK" / "MISMATCH" / "FAIL" per secret:

CAVEAT — JSON schema differences can cause a false MISMATCH: this does a
raw byte-for-byte string comparison, so if a local secret has an extra key
that the global secret doesn't carry (e.g. local has
{"username": ..., "token": ...} while global only has {"token": ...}), it
will report MISMATCH even though the meaningful value (the token) is
identical. Always `jq` both sides and diff the actual fields before
concluding a real problem.
